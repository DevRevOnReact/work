JobPilot. Расход токенов и техническая архитектура

Дата проверки — 27 ноября 2026 года. Начало замеров UTC — 2026-11-27T01:10:19.603596+00:00. Проверена действующая функция генерации на VPS. Вопросы синтетические, подбор резюме использует текущий профиль. В отчёте сохранены только размеры профессионального контекста.

Помощник генерирует ответы локально на VPS через Ollama и gemma3:4b. Модель имеет 3.9B параметров, формат gguf, квантование Q4_K_M. Идентификатор весов — 68ceab7e468a31c988b44d5a4984a0e21f58c4f7158c6ce29c1804babac38df7.

Фактические измерения

Вход включает системную инструкцию, служебное оформление диалога и JSON с вопросом, вакансией, пожеланием, языком и выбранными фактами резюме. Выход включает JSON-обёртку ответа. Сумма равна входу плюс выходу. Время включает подбор контекста и модель, для строки OCR также распознавание. Скорость рассчитана только по времени генерации Ollama.

Всего в эксперименте — 4599 входных + 913 выходных = 5512 токенов. Это точные счётчики конкретных запусков. Они меняются вместе с вопросом, выбранным резюме и длиной ответа.

Первый вызов включал загрузку модели за 7.14 с. У повторного английского запроса обработка входа заняла 0.43 с при тех же 818 входных токенах. Это эффект внутреннего кеша Ollama. Рабочий кеш готового ответа в PostgreSQL полностью пропускает вызов модели.

Только OCR тестового изображения занял 0.307 с. Его 35 распознанных символов затем вошли в промпт сценария OCR. Полная обработка этого сценария заняла 15.084 с.

Подход к измерению

  1. Через SSH прочитаны действующие URL сервисов, контейнеры, ограничения и закрытая сеть Docker. Проверены /api/version, /api/tags и /api/ps у локального Ollama.
  2. Скрипт импортирует установленную функцию prepare(), затем generate(). Перехват ответа HTTP выполняется только внутри отдельного процесса измерения. Тело запроса, схема JSON, настройки и выбор фактов совпадают с рабочим помощником.
  3. Счётчики prompt_eval_count и eval_count прочитаны из ответа Ollama. Время получено из duration-полей в наносекундах и perf_counter для полного сценария. Подсчёт символов в токены не применялся.
  4. Запросы выполнялись последовательно, перед каждым проверялось отсутствие queued/working черновиков пользователя. Черновики и уведомления экспериментом не создавались. Другие серверные задачи могли влиять на время.
  5. Первый английский вопрос повторён напрямую для наблюдения вариативности вывода. Такой повтор намеренно вызывает модель. Повтор через рабочий ReplyWorker может получить готовый результат из PostgreSQL.

Исходные счётчики, настройки, хеши файлов установленной генерации и тестовые входы находятся в JSON рядом с отчётом. Файл CSV содержит числовую таблицу. Личные факты резюме и ответы модели в выгрузку не включены.

8192 — вместимость контекста, а 280 — верхний предел генерации за вызов. Они не равны фактическому расходу каждого запроса. Ошибка проверки JSON после генерации всё равно расходует обработанные и сгенерированные токены.

Техническая схема

Стрелки показывают основные обращения, ответы идут обратно по тому же пути. Next.js и FastAPI находятся в контейнере app. PostgreSQL использует отдельную Docker-сеть default. Приложение соединено с default и assistant-private. Веса модели, база и артефакты размещены в отдельных Docker volumes.

Путь Android — HTTPS → nginx → Next.js /api/phone → FastAPI /mobile-assistant. Сервер сверяет SHA-256 личного ключа устройства с записью разрешённого устройства. Веб использует вход владельца, Telegram Mini App — проверку initData. ReplyWorker подбирает резюме, проверяет повтор, выполняет локальную генерацию и сохраняет результат. Телефон опрашивает status/answers. Telegram опрашивается сервером через getUpdates по исходящему HTTPS. Telegram Outbox доставляет уведомления, когда это запрошено.

Для OCR выбранный фрагмент уходит в assistant-media. Tesseract возвращает текст, который пользователь проверяет перед генерацией. Голос обрабатывает whisper.cpp small. Telegram получает сообщения и вложения, переданные через бот. Обычная работа поиска и откликов обращается к внешним сайтам вакансий и ATS.

Что означают результаты

Для локальной модели расход токенов характеризует вычислительную нагрузку. Счёт от внешнего LLM-провайдера за эти вызовы отсутствует. Оплата VPS определяется вашим тарифом. Стоимость электричества, CPU-секунды в рублях и ежемесячный платёж в этом исследовании не измерялись.

Точный расход прошлых запросов восстановить по reply_drafts нельзя. Рабочая функция сохраняет текст ответа и факты, но отбрасывает счётчики Ollama. Для постоянного учёта потребуется сохранять на каждую попытку model/digest, input/output tokens, duration, done_reason, признак повторного использования и итог проверки JSON. Изменение приложения в рамках этого исследования не выполнялось.

Во время измерения 2 из 7 сценариев завершились ошибкой подготовки ответа. У некоторых ответов done_reason=length: модель достигла лимита 280 токенов, после чего JSON не прошёл проверку. Требуется отдельно исправить ограничение длины и повторно проверить полноту JSON. Таблица сохраняет фактически потраченные токены этих попыток.

Проверка источников

Сведения о размещении подтверждены SSH-проверкой Docker и URL действующего приложения. Значения токенов получены от установленного Ollama, параметры — из установленного reply_assistant.py. Поведение повторов подтверждено reply_runtime.py. Поля API описаны в документации Ollama Chat, сведения о загруженных моделях — в Ollama /api/ps.
